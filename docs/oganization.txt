Source is organized by feature, not by client vs server.

Each domain folder holds the code for one gameplay concern: path (route follow), spaceobjects (planets, asteroids, and shell projection), hazards (incoming asteroids), encounters (stop waves and completion), and networking (room message schemas). Client and server still share one TypeScript tree. When behavior differs, the domain's setup function branches with isServer() instead of living under a client/ or server/ folder.

src/index.ts is the composition root. It wires domains (setupEncounters, setupHazards, setupSpaceObjects, the ship path system) and keeps the mission room plus HUD at that layer. Truly shared math and the debug teleport stay in utilities.ts. The visible ship entity and its virtual pose stay in ship.ts because many domains read and write them. The HUD stays in ui.tsx. Authored map data stays in path/routedata.ts because the path editor overwrites that file.

Tunable numbers and strings live in src/constants.ts so they can be adjusted in one place. They are grouped by feature. Each group starts with a MARK comment so the VS Code outline can jump to Ship, Path, Projection, Hazards, and so on. Names are prefixed and spelled out so they still make sense in that file, away from the original module (for example PATH_START_STOP_ID, PLANET_ENCLOSING_SPHERE_RADIUS, HAZARD_SPAWN_INTERVAL).

Constants.ts is for tuning, not for everything that happens to be a const. Route table data stays in routedata.ts. Message schemas stay in networking/messages.ts. ECS components stay next to the systems that define them.
